# 17.1 Project Structure

---

# 17.1.1 Purpose

The Project Structure defines the organization of the LexisGraph frontend codebase. A well-defined structure improves maintainability, scalability, developer productivity, and enables AI-assisted development by providing predictable locations for application components.

The frontend shall follow a modular, feature-oriented architecture based on the Next.js App Router while separating presentation, business logic, state management, and infrastructure concerns.

---

# 17.1.2 Objectives

The project structure shall:

- Promote modular development.
- Encourage code reuse.
- Separate business logic from UI.
- Improve maintainability.
- Support scalable feature development.
- Simplify onboarding.
- Enable AI code generation.
- Maintain consistency across the application.

---

# 17.1.3 Design Principles

The project structure shall follow these principles:

- Feature-first organization.
- Single responsibility.
- Separation of concerns.
- Reusable UI components.
- Centralized API communication.
- Type safety.
- Minimal coupling.
- Maximum cohesion.

Every directory shall have a clearly defined responsibility.

# 17.1.6 App Directory

The `app/` directory contains application routes using the Next.js App Router.

Example structure:

```
app/

layout.tsx

page.tsx

login/

dashboard/

policies/

reports/

organizations/

admin/

settings/

error.tsx

loading.tsx

not-found.tsx
```

Responsibilities:

- Routing
- Layout composition
- Server Components
- Metadata
- Error boundaries

Business logic shall not reside inside route files.

```
components/

feedback/

navigation/

providers/
```

# 17.1.8 Features Directory

Feature modules shall encapsulate business functionality.

```
features/

authentication/

dashboard/

policies/

reports/

analysis/

organizations/

users/

admin/

notifications/
```

Each feature shall contain:

```
components/

hooks/

services/

schemas/

types/

utils/
```

Feature modules shall not directly depend on other features.

---

# 17.1.9 Services Directory

```
services/

api/

auth/

analysis/

policies/

reports/

dashboard/

organization/
```

Responsibilities:

- API communication.
- Request construction.
- Response transformation.
- Error handling.

UI components shall never perform direct HTTP requests.

---

# 17.1.10 Stores Directory

Global application state shall be managed using Zustand.

```
stores/

auth.store.ts

theme.store.ts

notification.store.ts

sidebar.store.ts

organization.store.ts
```

Only shared state shall exist in global stores.

Feature-specific state shall remain local whenever possible.

# 17.1.19 Dependency Rules

Allowed dependency flow:

```
Pages

↓

Features

↓

Components

↓

Hooks

↓

Services

↓

API Client
```

Forbidden:

- Component → Database
- Component → Environment Variables
- Feature → Feature (direct coupling)
- UI → HTTP Client

# 17.1.21 Scalability Guidelines

The project structure shall support:

- Additional modules.
- Additional dashboards.
- Mobile applications.
- White-label deployments.
- Multi-tenancy.
- Internationalization.
- Plugin architecture.

New features shall be added without modifying existing modules whenever possible.

---

# 17.1.22 Best Practices

Developers shall:

- Keep files focused.
- Avoid deeply nested directories.
- Reuse components.
- Avoid duplicated logic.
- Keep components small.
- Write strongly typed code.
- Use feature modules.
- Follow naming conventions.

---

# 17.1.23 Acceptance Criteria

The project structure shall be considered complete when:

✓ Features are modular.

✓ Components are reusable.

✓ API logic is centralized.

✓ Global state is isolated.

✓ Shared utilities are reusable.

✓ Directory responsibilities are clearly defined.

✓ The architecture supports future growth.

---

# 17.1.24 Summary

The Project Structure establishes the architectural foundation of the LexisGraph frontend. By organizing the application into modular feature-based directories with clear responsibilities, the structure promotes maintainability, scalability, and developer productivity. This organization also enables AI-assisted development by providing a predictable, consistent layout that supports long-term evolution of the application while minimizing coupling between modules.
