# 17.5 State Management

---

# 17.5.1 Purpose

The State Management architecture defines how application data is stored, accessed, synchronized, and updated throughout the LexisGraph frontend. It establishes clear boundaries between local component state, global application state, server state, and persistent client state to ensure scalability, maintainability, and predictable behavior.

The frontend shall use lightweight state management while avoiding unnecessary global state.

---

# 17.5.2 Objectives

The State Management architecture shall:

- Separate UI state from business data.
- Centralize shared application state.
- Cache server data efficiently.
- Minimize unnecessary re-renders.
- Improve maintainability.
- Support optimistic updates.
- Enable predictable state transitions.
- Support future scalability.

---

# 17.5.3 Technology Stack

| State Type | Technology |
|------------|------------|
| Local UI State | React useState |
| Shared Client State | Zustand |
| Server State | TanStack Query |
| Forms | React Hook Form |
| Validation | Zod |
| Persistent Preferences | Local Storage |

---

# 17.5.4 State Categories

The application shall classify state into four categories.

```
Local Component State

↓

Shared Global State

↓

Server State

↓

Persistent Client State
```

Each category shall have a dedicated management strategy.

---

# 17.5.5 Local Component State

Local state shall be used for:

- Modal visibility.
- Dropdown menus.
- Input focus.
- Temporary selections.
- UI animations.
- Accordion state.
- Form steps.

Example

```tsx
const [isOpen, setIsOpen] = useState(false);
```

Local state shall not be shared across unrelated components.

---

# 17.5.6 Global Application State

Global state shall contain only data shared across multiple features.

Examples

- Authenticated user.
- Selected organization.
- Current theme.
- Sidebar state.
- Notification preferences.

Global state shall be implemented using Zustand.

---

# 17.5.7 Server State

Server state shall include:

- Dashboard data.
- Policies.
- Reports.
- Users.
- Organizations.
- Compliance analyses.
- Notifications.

Server state shall be managed exclusively through TanStack Query.

The frontend shall never duplicate server state inside Zustand.

---

# 17.5.8 Persistent State

Persistent state shall survive browser refreshes.

Examples

```
Theme

Sidebar Collapse State

Language Preference

Recently Selected Organization

Dashboard Preferences
```

Persistent state shall be stored using browser storage.

Sensitive information shall never be persisted in local storage.

---

# 17.5.9 State Architecture

```
Backend API

↓

TanStack Query

↓

Feature Hooks

↓

Components

↓

User Interaction

↓

Mutation

↓

API

↓

Cache Update
```

Business data shall flow through TanStack Query.

---

# 17.5.10 Zustand Stores

The frontend shall maintain the following stores.

```
auth.store.ts

theme.store.ts

sidebar.store.ts

organization.store.ts

notification.store.ts
```

Stores shall remain focused on a single responsibility.

---

# 17.5.11 Auth Store

Responsibilities

- Authentication status.
- Logged-in user.
- Access token metadata.
- User roles.
- Organization context.

Example

```ts
{
    user,
    isAuthenticated,
    organization,
    role
}
```

Authentication shall remain synchronized with secure HTTP-only cookies.

---

# 17.5.12 Theme Store

Responsibilities

```
Current Theme

System Theme

Dark Mode

Light Mode
```

Theme changes shall immediately update the UI.

---

# 17.5.13 Sidebar Store

Responsibilities

```
Collapsed State

Pinned State

Mobile Drawer

Expanded Sections
```

The sidebar state shall persist across sessions.

---

# 17.5.14 Organization Store

Responsibilities

```
Selected Organization

Organization Details

Available Organizations (Future)

Permissions
```

Changing the organization shall invalidate organization-specific server caches.

---

# 17.5.15 Notification Store

Responsibilities

```
Unread Count

Notification Visibility

Toast Queue
```

Historical notifications shall be fetched from the backend.

---

# 17.5.16 TanStack Query

The platform shall use TanStack Query for:

- Fetching.
- Caching.
- Background synchronization.
- Pagination.
- Infinite scrolling.
- Automatic retries.
- Cache invalidation.

Example resources

```
Policies

Reports

Dashboard

Users

Organizations

Analysis
```

---

# 17.5.17 Query Keys

Query keys shall be standardized.

Examples

```
["dashboard"]

["policies"]

["policy", policyId]

["reports"]

["report", reportId]

["users"]

["organizations"]
```

Consistent query keys simplify cache management.

---

# 17.5.18 Cache Invalidation

Cache shall be invalidated after:

- Policy upload.
- Policy deletion.
- Report generation.
- Organization updates.
- User invitations.
- Profile changes.

Invalidation shall target only affected resources.

---

# 17.5.19 Optimistic Updates

Optimistic updates may be used for:

- Profile updates.
- Notification dismissal.
- Settings changes.
- Theme changes.

Critical compliance operations shall wait for server confirmation.

---

# 17.5.20 State Flow

```
User Action

↓

Component

↓

Hook

↓

API Service

↓

Backend

↓

Response

↓

TanStack Cache

↓

Component Re-render
```

State updates shall follow a predictable unidirectional flow.

---

# 17.5.21 Error State

State management shall handle:

- Loading.
- Success.
- Error.
- Empty.
- Refreshing.

Components shall render appropriate UI for each state.

---

# 17.5.22 Loading State

Loading indicators shall support:

- Initial loading.
- Background refresh.
- Pagination loading.
- Infinite scrolling.
- Mutation progress.

Skeleton components shall be preferred over spinners for large content.

---

# 17.5.23 Form State

Forms shall use React Hook Form.

Responsibilities

- Input values.
- Validation.
- Dirty tracking.
- Submission state.
- Error messages.

Forms shall not store their state globally.

---

# 17.5.24 State Synchronization

The application shall synchronize:

- Authentication status.
- Organization selection.
- Dashboard refresh.
- Notifications.
- Background job progress.

Synchronization shall occur automatically where possible.

---

# 17.5.25 Security

The state management layer shall:

- Never store API keys.
- Never store passwords.
- Avoid storing JWTs in local storage.
- Clear state after logout.
- Prevent unauthorized cache reuse.

Authentication shall rely on secure HTTP-only cookies.

---

# 17.5.26 Performance

The state architecture shall:

- Minimize global state.
- Prevent unnecessary re-renders.
- Cache API responses.
- Use selective subscriptions.
- Avoid duplicated state.

State updates shall affect only subscribed components.

---

# 17.5.27 Best Practices

Developers shall:

- Prefer local state whenever possible.
- Use Zustand only for shared client state.
- Use TanStack Query for server data.
- Avoid duplicating state.
- Keep stores focused.
- Use typed selectors.
- Invalidate caches carefully.

---

# 17.5.28 Acceptance Criteria

The State Management architecture shall be considered complete when:

✓ Local UI state remains component-scoped.

✓ Shared state is managed with Zustand.

✓ Server state is managed using TanStack Query.

✓ Forms use React Hook Form.

✓ Cache invalidation is implemented correctly.

✓ Authentication state is synchronized.

✓ Sensitive information is never persisted insecurely.

---

# 17.5.29 Summary

The State Management architecture provides a scalable and predictable strategy for managing application data in the LexisGraph frontend. By separating local state, global client state, server state, and persistent preferences, the architecture minimizes complexity while improving performance, maintainability, and security. Leveraging Zustand for shared client state and TanStack Query for server synchronization ensures efficient data flow and a responsive user experience.
