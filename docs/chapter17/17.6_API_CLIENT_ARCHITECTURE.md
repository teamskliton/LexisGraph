# 17.6 API Client Architecture

---

# 17.6.1 Purpose

The API Client Architecture defines how the LexisGraph frontend communicates with backend services. It establishes a centralized, secure, type-safe, and reusable HTTP communication layer responsible for authentication, request handling, response processing, error management, retries, and caching.

The frontend shall never communicate directly with databases, AI models, or infrastructure services. All communication shall occur exclusively through the Backend REST API.

---

# 17.6.2 Objectives

The API Client Architecture shall:

- Centralize all HTTP communication.
- Provide a reusable API client.
- Support authentication automatically.
- Handle request and response transformations.
- Standardize error handling.
- Integrate with TanStack Query.
- Maintain strong typing.
- Simplify future API versioning.

---

# 17.6.3 Technology Stack

| Layer | Technology |
|---------|------------|
| HTTP Client | Axios |
| Data Fetching | TanStack Query |
| Validation | Zod |
| Authentication | Secure HTTP-only Cookies |
| Language | TypeScript |

# 17.6.6 API Client Responsibilities

The API client shall:

- Execute HTTP requests.
- Attach authentication automatically.
- Handle retries.
- Transform responses.
- Handle common errors.
- Log request failures.
- Support request cancellation.
- Maintain type safety.

---

# 17.6.7 API Layer Separation

The frontend shall separate responsibilities.

```
Components

↓

Hooks

↓

Services

↓

API Client

↓

Backend
```

Components shall never call Axios directly.

---

# 17.6.8 Base Configuration

The API client shall define:

- Base URL
- Request timeout
- Default headers
- Credentials policy
- JSON serialization
- API version

Example

```ts
Base URL:
/api/v1
```

---

# 17.6.9 Authentication

Authentication shall use secure HTTP-only cookies.

The client shall automatically send:

```
credentials: include
```

No JWT shall be manually stored in:

- Local Storage
- Session Storage
- Zustand

---

# 17.6.10 Request Interceptors

Request interceptors shall:

- Attach credentials.
- Add organization identifier.
- Add request ID.
- Add correlation ID.
- Set content type.
- Attach locale information.

Interceptors shall not contain business logic.

---

# 17.6.11 Response Interceptors

Response interceptors shall:

- Normalize responses.
- Handle unauthorized responses.
- Redirect expired sessions.
- Parse validation errors.
- Trigger global notifications.

---

# 17.6.12 Error Handling

The client shall standardize errors.

Supported categories:

```
400 Bad Request

401 Unauthorized

403 Forbidden

404 Not Found

409 Conflict

422 Validation Error

429 Rate Limited

500 Internal Server Error

503 Service Unavailable
```

Every error shall be converted into a consistent application format.

---

# 17.6.13 Error Model

Example

```ts
{
    code: "POLICY_NOT_FOUND",
    message: "...",
    details: {}
}
```

The frontend shall avoid displaying raw server errors.

---

# 17.6.16 Response Model

Successful responses shall be strongly typed.

Example

```ts
interface ApiResponse<T> {
    data: T;
    message: string;
}
```

The frontend shall validate critical response structures.

---

# 17.6.17 Query Integration

TanStack Query shall consume service functions.

Example

```
Dashboard

↓

dashboardService.getSummary()

↓

Query Cache

↓

Dashboard Component
```

Services shall remain independent of UI components.

# 17.6.18 Mutations

Mutations shall support:

- Policy upload.
- Report generation.
- User creation.
- Organization updates.
- Profile changes.

Mutations shall invalidate affected caches after success.

---

The API client shall support:

- Multipart uploads.
- Progress tracking.
- Upload cancellation.
- Retry on network failure.

Supported documents

```
PDF

DOCX

TXT

Markdown
```

---

# 17.6.20 File Download

Downloads shall support:

- Reports
- Policies
- Exported findings
- Audit reports

Supported formats

```
PDF

DOCX

CSV

JSON
```

---

# 17.6.21 Request Cancellation

Long-running requests shall support cancellation.

Examples

- Large uploads.
- Search.
- Report exports.

The frontend shall cancel obsolete requests automatically.

---

# 17.6.22 Retry Strategy

Automatic retries may occur for:

- Network interruptions.
- Temporary server failures.
- Gateway timeout.

Retries shall not occur for:

- Validation errors.
- Authentication failures.
- Permission errors.

---

# 17.6.23 Logging

Development mode may log:

- Request URL.
- Response time.
- Status code.
- Retry count.

Production logging shall exclude sensitive information.

---

# 17.6.24 Security

The API client shall:

- Never expose secrets.
- Never expose tokens.
- Validate request payloads.
- Sanitize user input.
- Prevent duplicate submissions.
- Respect backend authorization.

---

# 17.6.25 Performance

The API layer shall:

- Reuse connections.
- Cache GET requests.
- Deduplicate identical requests.
- Support pagination.
- Batch updates where applicable.

---

# 17.6.26 Future Enhancements

The architecture shall support:

- GraphQL integration.
- WebSocket communication.
- Server-Sent Events.
- Offline synchronization.
- API version negotiation.
- Multi-region endpoints.

---

# 17.6.27 Best Practices

Developers shall:

- Never call Axios from components.
- Keep services domain-specific.
- Keep API models strongly typed.
- Centralize error handling.
- Reuse service methods.
- Minimize duplicated requests.
- Separate API logic from UI.

---

# 17.6.28 Acceptance Criteria

The API Client Architecture shall be considered complete when:

✓ All backend communication is centralized.

✓ Authentication is handled automatically.

✓ Services are domain-specific.

✓ Errors are standardized.

✓ TanStack Query integration is complete.

✓ File uploads and downloads are supported.

✓ API communication remains type-safe.

---

# 17.6.29 Summary

The API Client Architecture provides a centralized, secure, and maintainable communication layer between the LexisGraph frontend and backend services. By encapsulating HTTP communication within reusable service modules and integrating seamlessly with TanStack Query, the architecture ensures consistent request handling, efficient caching, standardized error management, and strong type safety while keeping UI components independent of networking concerns.
